# Embeddings and candidate retrieval — Prompt 006

## Boundaries

`compatibility.domain` contains immutable request, candidate, feature and embedding values. `EmbeddingProvider` and `CandidateRetrievalPort` are application ports; the official OpenAI SDK, JDBC and pgvector operators remain inside infrastructure. `RetrieveCompatibilityCandidates` is internal application functionality. There is no new HTTP endpoint, MatchSession, MatchResult, score or final ranking implementation.

**Vector similarity is a candidate-retrieval signal only. It is not Couple Match Score. Retrieval order is not final user ranking.**

## Descriptor

`EmbeddingDescriptorFactory` emits `compatibility-descriptor-v1`, with fixed field order, sorted token lists, stable whitespace and SHA-256 hash. The fields are category, subcategory, primary/secondary colors, pattern, material appearance, fit, formality, seasonality, style tags and details. Missing descriptors use empty lists; missing subcategory uses `UNKNOWN`.

Product input is its canonical category/subcategory and `ProductAttributes`; analysis input is immutable `AnalysisRevision.attributes`. Existing ProductAttributes has no details field, so that product descriptor line is empty. There is no schema expansion of Product in this prompt. Names and brands are deliberately omitted to keep the descriptor confined to structured style attributes and avoid unconstrained catalogue prose. Target remains an explicit relational constraint and is omitted from both vectors. These choices align the source and product vocabularies without inferring a person's gender.

Prices, currency, URLs, affiliate data, retailer identifiers, feed data, availability, images, ownership information and provider responses cannot enter this descriptor through its typed inputs. The descriptor is constructed deterministically, not generated by an LLM. Changing semantics requires a new descriptor version and re-embedding.

## Model and vector space

The default configured model is `text-embedding-3-small`, with explicit 1536-dimensional output. OpenAI documents this model's default dimension as 1536; the existing official Java SDK supports the embeddings endpoint and explicit dimensions. This is a straightforward text embedding baseline, not a measured claim about fashion retrieval quality. Provider defaults to `disabled`; enabling it requires `EMBEDDING_PROVIDER=openai` and `OPENAI_API_KEY`. `OPENAI_EMBEDDING_MODEL` selects the model.

Configuration under `coupleoutfit.ai.embeddings` controls model, dimensions, connect timeout (5 seconds default; maximum 10), request timeout (20 seconds default; maximum 30), attempts (2 default; 1–3) and retry backoff (250 ms times retry number; base maximum 2 seconds). Dimensions must equal the migrated `vector(1536)` columns at startup. A different supported model may use the same explicit dimension with separate metadata. Changing dimension requires a later migration and separate/replacement compatible storage, never padding or truncation in application code.

Timeouts, network errors, HTTP 429/408 and 5xx receive bounded retries. Invalid response, unexpected model, dimension mismatch and authentication failures do not. Vectors must be finite, nonempty and nonzero for cosine distance. SDK retries, redirects and logging are disabled; no SDK type or raw provider exception escapes infrastructure. The provider request sends only descriptor text, configured model, dimensions and float encoding. Missing credentials fail embedding calls safely without affecting startup or readiness. Normal CI never calls OpenAI.

References: [OpenAI embedding guide](https://developers.openai.com/api/docs/guides/embeddings), [Java embeddings API](https://developers.openai.com/api/reference/java/resources/embeddings/methods/create).

## Storage, generation and concurrency

V6 adds only `product_embedding` and `analysis_embedding`. Each row contains subject FK, `STYLE_COMPATIBILITY` type, provider/model/dimensions, descriptor version/hash, source version/timestamp, vector, safe provider request reference and UTC timestamps. ProductEmbedding and AnalysisEmbedding expose neutral embedding data; no vector-specific persistence type reaches the domain.

Uniqueness covers subject, type, provider, model, descriptor version and source version. Product source version combines the persisted Product update timestamp and descriptor hash. Analysis source version is the immutable revision UUID. Older versions remain alongside newer rows. Product changes must maintain the existing `updatedAt` contract; retrieval joins `source_updated_at = product.updated_at`, so stale versions are excluded. No offer changes influence style embedding generation.

`EnsureProductEmbedding` loads canonical Product data and explicitly prepares one embedding. `prepareBatch` accepts at most 50 product IDs, deduplicates them and executes sequentially. It stops on failure; completed items remain reusable. There is no scheduler or bulk feed ingestion. Retrieval never prepares catalogue embeddings implicitly.

`EnsureAnalysisEmbedding` accepts an explicit immutable revision. Normal retrieval loads the owned SourceItem and its current completed analysis revision, reuses or generates that revision's embedding, and rechecks that it is still current before querying candidates. The existing model has no separate approval status; COMPLETED/current is the authoritative boundary. An explicitly requested historical revision may be prepared internally; normal retrieval never silently selects revision 1 after correction.

Generation uses short transactions: insert a unique row as an in-flight claim, commit, call the provider outside a transaction, then complete that claim with the validated vector. A nullable vector and null completion time represent an in-flight claim only; these rows are never candidates or reusable completed embeddings. This is a deliberate departure from a universally NOT NULL vector column to avoid holding transactions across provider calls or adding claim tables. The database checks vector/completion-time consistency. Failed generation removes only its uncompleted claim, allowing a later explicit retry. Competing calls reuse a completed row or receive `EMBEDDING_NOT_AVAILABLE` while generation is active. There are no distributed locks.

The claim UUID fences completion/deletion. A process crash may leave a vectorless claim. Timestamps support diagnosis; automatic claim takeover is intentionally absent, since recovery must ensure the old worker is no longer active before permitting another provider call. Future retention/recovery must respect source/revision foreign keys. There is no history or retention UI.

## Candidate eligibility and offers

A single parameterized SQL query joins vector rows, Product, ProductOffer, RetailerMarket, Retailer and reference data. All filters are applied in SQL before selecting the limited result set:

- Embedding provider/model/dimension/descriptor version matches the source embedding; vector exists and product version is current.
- Country, default currency and locale equal the request's persisted market context.
- Country, currency, locale, retailer and retailer market are active.
- RetailerMarket has both catalogue and matching enabled.
- Product is ACTIVE and matches the explicitly requested ProductTarget.
- Candidate category follows CategoryEligibilityPolicy: broad existing categories except ACCESSORY. No additional cross-category styling rules are invented.
- ProductOffer is active and availability is IN_STOCK or UNKNOWN; OUT_OF_STOCK is excluded.
- Price is not required for semantic candidate retrieval. When a price exists, its currency must match the requested market. Missing-price offers may remain eligible and retain their absent price; later presentation may indicate unavailable/stale pricing. Price magnitude never influences embedding or similarity.

UNKNOWN availability remains explicit candidate data for later ranking confidence decisions; no penalty is scored now. The default primary-category policy excludes accessories in accordance with Prompt 006; no repository UX rule was found requiring them. Footwear and OTHER remain eligible under the broad policy.

Embeddings describe Product style. Every returned candidate identifies an eligible concrete ProductOffer and RetailerMarket. Multiple eligible offers collapse to one per product: IN_STOCK before UNKNOWN, then lowest offer UUID. Similarity never bypasses eligibility. Market is never inferred from domain strings. No same-retailer restriction or affiliate URL appears in compatibility objects.

## Retrieval and features

Exact cosine distance uses pgvector `<=>`. Ordering is ascending distance with product UUID as the stable tie breaker. The exposed semantic feature is `clamp(1 - cosineDistance, 0, 1)`; negative cosine similarities become zero. The pre-ranking candidate limit is explicit per request, validated to 1–200; 50 is the documented example, not a UI result count.

Candidate records carry product/offer/retailer-market IDs, category, target, attributes, availability and semantic similarity. CompatibilityFeatures copies source/candidate colors, patterns, formality, tags and seasons directly from canonical attributes. No color harmony, pattern compatibility, seasonal weighting or final score is computed.

The SQL returns all required candidate data in one query. Mapping a row performs no repository call, so there is no per-candidate N+1 query. Source loading and optional source embedding preparation add a fixed number of queries independent of candidate count. Empty eligibility returns an empty list.

Only primary-key/uniqueness indexes are created. Exact search is appropriate for the empty initial production catalogue and small fixtures; no measured latency or catalogue scale justifies HNSW. Introduce ANN only after measuring eligible catalogue size, latency and recall under these same relational filters. No IVFFlat is added.

## Security, observability and ADRs

Source ownership is reused; callers cannot supply a different commerce market through normal retrieval. No public vectors, diagnostic endpoints or provider secrets are exposed. Micrometer records embedding product/analysis generation, embedding failure, retrieval count/duration/empty results. Logs contain safe target, country and result counts; no vectors, descriptors or commercial URLs are logged.

ADR-001: persisted SourceItem market flows into SQL country/currency/locale filters. Tests exclude a perfect-similarity India candidate from a GB request; India exists only in isolated test fixtures, not production seeds.

ADR-017: CompatibilityRequest, CompatibilityCandidate, CompatibilityFeatures and CandidateRetrievalPort are reusable, relationship-neutral concepts. Embedding storage is shared retrieval infrastructure for future modes. This prompt does not implement those modes, Complete My Look, final same-retailer matching or Couple Match Score.

Tests use deterministic fixture geometry and synthetic SDK responses. They verify descriptors, versioning, concurrency, retries, vector integrity, V6 clean/V5 upgrades, market and target isolation, availability, stale/missing exclusion, deterministic offer choice and ordering. Fixture similarity proves mechanics, not fashion quality. Live provider evaluation is separate and has not been performed for this implementation.
